# Evidence Table — Subscription Health Data Product

_Generated by `scripts/build_evidence.py` from `evidence/evidence_sources.csv` and
`evidence/own_testing_claims.csv`. Do not edit by hand._

Every source is labeled with exactly one evidence type:

| Type | Meaning | How to weigh it |
|:--|:--|:--|
| vendor marketing | Published by a vendor about its own product (blogs, docs, reports) | Indicates capabilities and intent; treat performance and cost claims as unverified |
| peer-reviewed | Refereed conference or journal paper | Strong on mechanisms and trade-offs; workloads rarely match Aurora's scale |
| practitioner benchmark | Reproducible benchmark or survey by practitioners, often vendor-adjacent | Useful directional comparison; check who ran it and on what data |
| own testing | Aurora's own PoC, pilot or measurement | Only source that can confirm Aurora-specific claims; planned, not yet run |

Rows marked **⚑ OWN TESTING** are claims that **cannot be sourced externally**
and must be proven by Aurora's own testing before the corresponding ADR is accepted.

## Claims requiring own testing

External sources inform these claims but cannot settle them, because each one
depends on Aurora's data, workload, team, pricing or customers. All are **Open**
until the test runs and the result is recorded here.

#### ⚑ OWN TESTING — C-WL-01 (Warehouse vs lakehouse)

**Claim:** At Aurora's scale (<=1 TB stored, high scenario) the chosen platform serves retention dashboards at p95 < 5 s within its compute allocation.

- **Why external sources cannot settle it:** Public benchmarks run TPC-DS at 1-100 TB with tuned configs and list prices; Aurora's query mix, concurrency and negotiated pricing are unique.
- **Related assumptions:** A-STO-01, A-STO-03, A-BUD-01, A-BUD-02
- **Test method:** Build the 3 core retention marts on synthetic data sized to the high scenario on 2 shortlisted platforms; replay 2 weeks of dashboard query logs; record p95 latency, credits/DBUs and stored bytes.
- **Pass threshold:** p95 < 5 s at 20 concurrent users; projected compute <= 50% of A-BUD-01 base; measured compression within A-STO-01 range
- **Status:** Open

#### ⚑ OWN TESTING — C-WL-02 (Warehouse vs lakehouse)

**Claim:** The ML team can pull a 12-month churn feature set into training without a manual export copy.

- **Why external sources cannot settle it:** Depends on Aurora's ML stack (notebooks, feature store, connectors) and network/egress setup.
- **Related assumptions:** A-STO-03
- **Test method:** From each shortlisted platform, read the feature table into the ML team's training environment via native connector or open table format; time the extract and check schema/point-in-time correctness.
- **Pass threshold:** Full 12-month extract < 15 min; zero row-count or point-in-time mismatches vs source
- **Status:** Open

#### ⚑ OWN TESTING — C-OR-01 (Orchestration)

**Claim:** The chosen orchestrator can backfill 12 months of models and features within an 8-hour overnight window.

- **Why external sources cannot settle it:** Backfill time depends on Aurora's DAG size, partitioning and warehouse concurrency, not on the orchestrator alone.
- **Related assumptions:** A-GRW-02, A-EVT-02
- **Test method:** Run a full 12-month backfill of staging -> marts -> features on high-scenario synthetic data under each shortlisted orchestrator.
- **Pass threshold:** Backfill completes < 8 h with no manual restarts
- **Status:** Open

#### ⚑ OWN TESTING — C-OR-02 (Orchestration)

**Claim:** Asset/lineage-aware orchestration catches data-quality faults before retention-team consumers see them.

- **Why external sources cannot settle it:** Detection depends on Aurora's specific tests, freshness SLAs and failure modes.
- **Related assumptions:** —
- **Test method:** Seed 20 representative faults (late billing webhook, duplicated events, schema drift, null churn labels) and measure detection point and time.
- **Pass threshold:** >= 90% of seeded faults blocked before mart publish; median detection < 30 min
- **Status:** Open

#### ⚑ OWN TESTING — C-OR-03 (Orchestration)

**Claim:** A single analytics engineer can add a new model with tests and ownership metadata in under one working day.

- **Why external sources cannot settle it:** Team skill mix and local conventions dominate; surveys report averages across very different teams.
- **Related assumptions:** —
- **Test method:** Time-box onboarding exercise: two engineers each add one new mart + tests on each shortlisted orchestrator.
- **Pass threshold:** Median < 1 working day; no platform-team assistance required
- **Status:** Open

#### ⚑ OWN TESTING — C-ST-01 (Streaming vs micro-batch)

**Claim:** Retention interventions do not need data fresher than 15 minutes to change outcomes.

- **Why external sources cannot settle it:** Value of freshness depends on Aurora customer behavior and the retention team's intervention playbook; no external study covers it.
- **Related assumptions:** A-EVT-01, A-GRW-04
- **Test method:** From historical data, measure the lag between first churn signal (cancel-page visit, skip, failed payment) and the cancellation event; review intervention response times with the retention team.
- **Pass threshold:** Median signal-to-cancel lag > 1 h and retention team cannot act faster than 15 min => micro-batch accepted
- **Status:** Open

#### ⚑ OWN TESTING — C-ST-02 (Streaming vs micro-batch)

**Claim:** Micro-batch at 15-minute cadence absorbs high-scenario peak-day load within the ingestion budget.

- **Why external sources cannot settle it:** Burst shape on Aurora promo days and per-batch platform cost are workload-specific.
- **Related assumptions:** A-EVT-02, A-EVT-04, A-EVT-05, A-BUD-02
- **Test method:** Replay last BFCM clickstream scaled to the high scenario (~37.6M events/day) through the micro-batch pipeline; record end-to-end lag and cost.
- **Pass threshold:** p95 end-to-end lag < 20 min on peak day; ingestion spend <= A-BUD-02 ingestion allocation
- **Status:** Open

#### ⚑ OWN TESTING — C-AI-01 (Agentic AI)

**Claim:** Retrieval over Aurora transcripts finds the right supporting passages for retention-agent questions.

- **Why external sources cannot settle it:** Domain language, transcript quality and chunking interact; general embedding benchmarks do not predict Aurora recall.
- **Related assumptions:** A-TRN-02, A-TRN-04, A-TRN-05
- **Test method:** Label 200 real retention-agent questions with gold transcript passages; compare chunk sizes and 2-3 embedding models.
- **Pass threshold:** Recall@5 >= 0.85 on held-out set
- **Status:** Open

#### ⚑ OWN TESTING — C-AI-02 (Agentic AI)

**Claim:** The assistant's answers stay grounded in Aurora policy and transcripts and never leak PII.

- **Why external sources cannot settle it:** Hallucination and PII risk depend on Aurora's policies, redaction pipeline and red-team prompts.
- **Related assumptions:** —
- **Test method:** Run RAGAS-style faithfulness scoring plus a 150-prompt red-team set (policy invention, refund promises, PII extraction) against the assistant.
- **Pass threshold:** Faithfulness >= 0.95; unsupported policy statements < 1%; PII redaction recall >= 99%
- **Status:** Open

#### ⚑ OWN TESTING — C-AI-03 (Agentic AI)

**Claim:** A tool-using agent improves retention-task success enough over a fixed RAG workflow to justify its extra cost and variance.

- **Why external sources cannot settle it:** Agent gains reported on public benchmarks are task-specific and often ignore cost and run-to-run reliability.
- **Related assumptions:** A-BUD-03
- **Test method:** Run both designs on the same 200-task eval set (look up account, explain options, propose offer) with k=4 repeated trials each.
- **Pass threshold:** Adopt agentic only if task success +10 pts and pass^4 not lower than workflow at <= 2x cost
- **Status:** Open

#### ⚑ OWN TESTING — C-AI-04 (Agentic AI)

**Claim:** Cost per assistant conversation stays at or below the A-BUD-03 base value at acceptable latency.

- **Why external sources cannot settle it:** Token usage per conversation depends on Aurora's transcripts, prompts and model choice; vendor price sheets give rates, not usage.
- **Related assumptions:** A-BUD-03, A-BUD-02
- **Test method:** Two-week pilot with 10 retention agents; log tokens, cache hits, latency and cost per conversation.
- **Pass threshold:** Mean cost <= $0.05 per conversation; p95 latency <= 4 s
- **Status:** Open

#### ⚑ OWN TESTING — C-BAS-01 (Cross-cutting baselines)

**Claim:** Planning placeholders for churn, engagement and transcript length are within the register's low-high ranges.

- **Why external sources cannot settle it:** These are Aurora's own operating metrics; industry figures are only placeholders.
- **Related assumptions:** A-GRW-04, A-EVT-01, A-EVT-02, A-TRN-02
- **Test method:** Pull trailing-12-month cohort churn (billing), 30-day DAU and events/session (product analytics), and token length of a 1,000-transcript sample (helpdesk).
- **Pass threshold:** Each measured value falls within low-high; otherwise update register and re-run projections
- **Status:** Open

#### ⚑ OWN TESTING — C-BAS-02 (Cross-cutting baselines)

**Claim:** Component spend tracks the A-BUD-02 allocation and the total stays under the A-BUD-01 ceiling.

- **Why external sources cannot settle it:** Only Aurora's tagged cloud bill shows actual spend by component.
- **Related assumptions:** A-BUD-01, A-BUD-02
- **Test method:** Tag all data-platform resources by component; review 90 days of billing against allocation.
- **Pass threshold:** No component > 125% of its allocation; total run-rate <= A-BUD-01 base
- **Status:** Open
